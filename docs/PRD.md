## 1. 개요

**donotext**는 MarkText(오픈소스 마크다운 에디터)의 핵심 사용 경험을 재현한 **Electron 데스크톱 마크다운 에디터**이며, MarkText에 없는 **화면 분할 및 파일 비교(diff)** 기능을 추가한다.

| 항목 | 내용 | 상태 |
|---|---|---|
| 제품 형태 | Electron 데스크톱 앱 (Windows/macOS/Linux) | [확정] |
| 기준 제품 | MarkText (https://github.com/marktext/marktext) | [확정] |
| 추가 기능 | 창 분할로 여러 파일 내용 비교·분석 | [확정] |
| 구현 방식 | MarkText 코드 복사가 아닌, 구조 분석 후 신규 작성 | [가정] |

## 2. 배경 및 문제 정의

- MarkText는 실시간 WYSIWYG, 소스 모드, 집중/타자기 모드 등 완성도 높은 편집 경험을 제공한다 (README 확인).
- 그러나 여러 문서를 한 화면에서 나란히 열어 **내용을 대조·비교**하는 작업(버전 비교, 문서 간 정합성 점검, 번역/개정본 대조)을 에디터 안에서 하기 어렵다. 사용자는 별도 diff 도구나 창 여러 개를 오가야 한다.
- donotext는 "MarkText급 편집 경험 + 에디터 내장 분할/비교"를 한 앱에서 제공하는 것을 목표로 한다.

## 3. 목표와 비목표

### 목표
1. MarkText의 핵심 편집 경험(§5.1)을 동등한 수준으로 제공한다.
2. 화면 분할 + 비교 기능(§5.2)을 1급 기능으로 제공한다.
3. 로컬 파일을 직접 열고 저장하며, 데이터를 외부로 전송하지 않는다(오프라인 동작).

### 비목표 (v1 제외)
- 클라우드 동기화, 협업(실시간 공동 편집), 계정/로그인
- 모바일/웹 버전
- 플러그인 마켓
- MarkText의 모든 세부 설정·단축키 100% 일치 (핵심 경험 우선)

## 4. 대상 사용자 [가정]

- 마크다운으로 문서·노트·기술 문서를 작성하는 개인 사용자 및 실무자
- 여러 문서(버전/초안/참고본)를 대조하며 작업하는 사용자
- 설치형 로컬 앱과 오프라인 사용을 선호하는 사용자

## 5. 기능 요구사항

우선순위: **P0** = v1 필수, **P1** = v1 목표, **P2** = 후속.

### 5.1 편집 코어 (MarkText 동등)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| E-01 | 실시간 WYSIWYG 편집 (입력하면 즉시 서식 반영) | P0 |
| E-02 | CommonMark + GFM(표, 체크리스트, 취소선, 자동링크) 지원 | P0 |
| E-03 | 소스 코드 모드 ↔ WYSIWYG 모드 전환 | P0 |
| E-04 | 코드 블록(언어 지정, 구문 강조) | P0 |
| E-05 | 수식(KaTeX) 인라인/블록 | P1 |
| E-06 | front matter(YAML) 인식 | P1 |
| E-07 | 이모지 지원 | P2 |
| E-08 | 집중(Focus) 모드, 타자기(Typewriter) 모드 | P1 |
| E-09 | 클립보드 이미지 붙여넣기 → 파일로 저장 후 링크 삽입 | P1 |
| E-10 | 인라인 서식 단축키/단락 단축키 | P0 |
| E-11 | 실행 취소/다시 실행, 찾기/바꾸기 | P0 |
| E-12 | 다이어그램(Mermaid 등) | P2 [확인 필요: MarkText 지원 범위] |

### 5.2 화면 분할 및 비교 (핵심 차별 기능)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| S-01 | 편집 영역을 **가로/세로로 분할**, 재귀 분할(분할 창 안에서 다시 분할) 지원 | P0 |
| S-02 | 분할 창마다 **독립된 탭 묶음**을 가지며, 서로 다른 파일을 열 수 있음 | P0 |
| S-03 | 같은 파일을 두 창에서 열면 **내용 동기화**(한쪽 수정 시 다른 쪽 즉시 반영) | P0 |
| S-04 | 분할 경계선 **드래그로 크기 조절**, 더블클릭으로 균등 분할 | P0 |
| S-05 | 분할 창 닫기·병합, 탭을 다른 창으로 **드래그 이동** | P1 |
| S-06 | **비교(Diff) 모드**: 두 창의 문서를 줄 단위로 비교해 추가/삭제/변경을 하이라이트 | P0 |
| S-07 | 비교 모드에서 **스크롤 동기화**(켜기/끄기) | P0 |
| S-08 | 변경 지점 간 이동(다음/이전 차이), 차이 개수 표시 | P1 |
| S-09 | 단어 수준(인라인) 차이 하이라이트 | P1 |
| S-10 | 비교 모드에서 차이 블록을 한쪽으로 **병합(→ / ←)** | P2 |
| S-11 | 분할 레이아웃 **세션 복원**(재실행 시 마지막 레이아웃과 열린 파일 복원) | P1 |
| S-12 | 비교 결과를 내보내기(HTML/텍스트 diff) | P2 |

### 5.3 파일 및 앱 관리

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-01 | 파일 열기/저장/다른 이름으로 저장, 다중 탭 | P0 |
| F-02 | 폴더 열기 + 사이드바 파일 트리 | P0 |
| F-03 | 사이드바에서 파일/폴더 생성·이름 변경·삭제(삭제 전 확인) | P1 |
| F-04 | 사이드바 드래그로 파일/폴더 이동 (MarkText 최신 커밋에도 반영된 기능) | P2 |
| F-05 | 외부에서 파일이 변경되면 감지 후 다시 불러오기 안내 | P1 |
| F-06 | 저장하지 않은 변경 보호(닫을 때 확인), 자동 저장 옵션 | P0 |
| F-07 | 최근 파일 목록 | P1 |
| F-08 | 개요(목차) 패널 | P1 |
| F-09 | 내보내기: **HTML, PDF** | P1 |
| F-10 | 테마: 라이트/다크 최소 2종 + 사용자 선택 | P1 |

## 6. 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| 성능 | 1MB 이하 문서에서 입력 지연이 체감되지 않을 것(목표 입력 반영 < 50ms). 분할 창 4개 동시 열기에서도 동작할 것. [가정: 수치는 구현 시 측정으로 보정] |
| 안정성 | 비정상 종료 시 미저장 내용 복구용 임시 백업 제공 |
| 보안 | Electron `contextIsolation` 활성, `nodeIntegration` 비활성, preload로 IPC 최소 노출, 원격 콘텐츠 로드 금지, 마크다운 렌더링 시 HTML 살균(sanitize) |
| 개인정보 | 문서 내용 외부 전송·텔레메트리 없음 |
| 접근성 | 키보드만으로 분할/탭 이동/비교 이동 가능 |
| 국제화 | UI 한국어/영어 [가정: v1은 한국어 우선, 영어 병행 여부 확인 필요] |
| 플랫폼 | Windows/macOS/Linux 빌드. 개발 환경(클라우드 컨테이너)에서는 GUI 직접 검증이 제한적이므로 단위·통합 테스트 + 렌더러 브라우저 모드 검증을 병행 |

## 7. 사용자 시나리오

1. **버전 비교:** 사용자가 `보고서_v1.md`와 `보고서_v2.md`를 좌우로 열고 비교 모드를 켠다 → 변경/삭제/추가 줄이 색으로 표시되고, "다음 차이"로 이동하며 검토한다.
2. **참고 문서 대조:** 위쪽 창에 참고 문서, 아래쪽 창에 작성 중인 문서를 두고 스크롤을 동기화해 대조하며 작성한다.
3. **긴 문서 두 지점 동시 보기:** 같은 파일을 두 창에서 열어 서론과 결론을 동시에 보며 수정한다(S-03).

## 8. 기술 방향 (제안 — 사용자 승인 전)

| 영역 | 제안 | 상태 |
|---|---|---|
| 셸 | Electron + TypeScript | [제안] |
| 에디터 코어 | **TipTap(ProseMirror) 기반** WYSIWYG + 마크다운 직렬화. 분할 창마다 독립 에디터 인스턴스 | [제안, 승인 대기] |
| 소스 모드 | CodeMirror 6 | [제안] |
| 비교(diff) | 줄 단위 diff 라이브러리 + 단어 단위 보조 | [제안] |
| UI 프레임워크 | React 또는 Vue (설계 단계에서 결정) | [미정] |
| 빌드 | Vite 계열 번들러 + electron-builder | [제안] |
| 테스트 | 단위(Vitest), 컴포넌트/통합, Electron E2E(Playwright) | [제안] |

비교한 대안: B) MarkText의 편집 엔진 Muya 재사용, C) 자체 에디터 작성. A안을 추천하는 이유는 분할 창별 독립 상태 구성이 쉽고 검증된 확장으로 표·코드·수식을 처리할 수 있어 구현 위험이 낮기 때문이다.

> MarkText 내부 구조(Muya, Vue)와 MIT 라이선스는 사전 지식이며 **[확인 필요]**. 코드를 일부라도 재사용하게 되면 라이선스 고지 의무를 먼저 확인한다.

## 10. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| WYSIWYG ↔ 마크다운 왕복 시 서식 손실 | 데이터 신뢰도 저하 | 왕복 테스트 코퍼스, 지원 문법 범위 명시 |
| 분할 창 다수에서 성능 저하 | 입력 지연 | 비활성 창 렌더 최적화, 대용량 파일 경고 |
| "똑같이"의 해석 차이 | 기대 불일치 | §5.1 범위를 사용자와 합의 후 고정 |
| 개발 환경에서 GUI 검증 제한 | 검증 누락 | 렌더러 브라우저 모드 + E2E, 로컬 최종 확인 안내 |
| 라이선스 | 법적 위험 | 신규 작성 원칙, 재사용 시 고지 |
| 보안(마크다운 내 HTML/스크립트) | XSS | 살균 및 Electron 보안 설정 |

## 12. 미결 사항 (사용자 확인 필요)

1. 에디터 코어 A안(TipTap/ProseMirror) 승인 여부.
2. "똑같이"의 범위: §5.1 목록 중 빠져야 할 것/더 필요한 것.
3. UI 언어(한국어 전용 vs 한/영).
4. 비교 모드 병합 기능(S-10)을 v1에 포함할지.
5. 배포 대상 OS 우선순위 (예: Windows 우선).
6. 파일 형식: `.md` 외 `.markdown`/`.txt` 허용 여부.
